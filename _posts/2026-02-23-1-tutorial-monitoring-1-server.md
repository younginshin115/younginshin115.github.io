## 들어가면서

저는 현재 다니고 있는 회사에서 나홀로 데이터 엔지니어로서 데이터 수집부터 모델 배포까지 아우르는 데이터, 모델 통합 플랫폼을 설계, 구축, 운영하고 있습니다. 데이터 엔지니어링에는 자신이 있었지만 플랫폼 운영은 처음하는 일이기에 우여곡절이 많았습니다. 그 중 가장 당황스러웠던 것은 서버가 갑자기 죽는 일이었습니다. '영인님, 서버가 멈췄어요!' 라는 메시지를 받으면 자다가도 일어나서 되살리고 아침에 눈 뜨면 서버가 괜찮을까 제일 먼저 켜보고는 했습니다. 제 불편도 불편이었지만 무엇보다 우려되는 것은 이용자의 불편함이었습니다.

그래서 저는 이 문제를 해결하기 위해 제가 제일 잘하는 일을 하기로 했습니다. 바로 데이터를 눈에 보이게 하는 일이었습니다. 문제를 해결하기 위해서는 원인이 무엇인지 알아야 했습니다. 서버가 죽는 원인이 CPU인지, 메모리인지, 사용 패턴은 무엇인지 확인할 필요가 있었습니다. 그래서 저는 시간에 따라 서버 자원 사용량을 모니터링할 수 있는 대시보드를 구축했습니다. 

해당 대시보드를 통해 사용량 패턴을 확인했습니다. 특정 시점에 피크가 튄다면 해당 시점에 수행된 프로세스를 찾아 문제를 분석했습니다. 만약 꾸준히 사용량이 높다면 운영 리소스에서 문제가 있다는 뜻이므로 해당 코드를 최적화하고, 정말 더 이상 최적화가 될 수 없는 데도 여전히 평균값이 높다면 그때는 서버 리소스를 확장하는 식으로 해결했습니다. 무엇보다 병목이 되는 리소스가 무엇인지 한 눈에 알 수 있어서 빠르게 원인을 찾고 해결할 수 있었습니다.

이렇게 대시보드를 통해 문제를 해결해나가면서 경험적으로 문제가 발생하는 임계값이 보이기 시작했습니다. cpu가 이 정도 수치를 넘으면 조치를 취해야 한다거나, 이 시점에는 유저의 접속량이 많아서 어느정도까지는 허용 범위라거나 하는 저 나름대로의 기준이 생겼습니다. 그 기준에 맞춰서 대시보드에 특정 임계값이 넘으면 제게 알람을 보내도록 설정했습니다. 알람을 설정하자 문제가 발생하기 전에 조치를 취해 문제를 미연에 방지할 수 있었습니다. 그 덕분에 3년 동안 서버 다운 없이 안정적으로 서버를 운영할 수 있었습니다. 또한, 알람 시스템을 구축한 이후에는 대시보드를 계속 들여다 볼 필요가 없어졌습니다. 알람이 왔을 때만 들어와서 현황을 파악하는 식으로 업무 패턴이 바뀌었고, 그렇게 확보한 시간은 신규 서비스 구현과, 기존 서비스 유지보수라는 더 중요한 일에 투자할 수 있었습니다.

항상 문제가 생길 때 마다 구축하기 정말 잘 했다고 생각하는 대시보드이기 때문에 저와 같은 상황에 있는 분들께 도움이 되고 싶은 마음에 이 글을 작성하게 되었습니다. 제가 모니터링 하고 있는 지표와 어떤 점을 중요하게 보고 있는지를 공유하고자 합니다. 이 글을 읽고 계시는 분들도 제 대시보드를 참고하셔서 처하신 상황에 맞는 대시보드를 구현하실 수 있기를 응원합니다.

## Quick Overview
<p><img src="/assets/images/260223/01.png" /></p>

이 영역은 서버 상태를 한 눈에 확인하기 위한 요약 섹션입니다. 대부분의 경우에는 이 섹션만 확인합니다. 여기서 이상 징후가 보이면 아래 상세 지표에서 추가로 확인하는 식입니다.

### Uptime

Uptime은 서버가 마지막으로 재부팅된 이후 얼마나 가동되었는지를 보여주는 지표입니다.

운영 초반에는 장애 여부를 확인하는 용도로 봤지만, 지금은 오히려 재부팅 시점을 판단하는 기준으로 사용하고 있습니다.

서버를 장기간 켜두면 메모리 사용량이나 CPU 사용 패턴이 점점 비정상적으로 누적되는 경우가 있었습니다. 특히 컨테이너 기반 환경에서는 장시간 실행된 프로세스가 완전히 정리되지 않는 경우도 있었고, 메모리 사용량이 서서히 증가하는 패턴도 관찰했습니다.

그래서 일정 기간(예: 몇 달 이상) 가동된 경우에는 업데이트나 점검 시점에 맞춰 한 번 재부팅을 진행합니다.

### CPU Usage

CPU의 사용량을 비율로 표시한 지표입니다. 80%가 넘으면 노란색으로 표시되며 제게 알림이 오도록 설정해놓았습니다. 90%가 넘으면 빨간색으로 표시하게 해두었지만 그 전에 조치를 취하기 때문에 볼 일은 자주 없습니다. 

저는 알람을 받게 되면 먼저 패턴을 확인합니다. 일시적인 피크인지, 지속적으로 CPU가 높은 상황인지에 따라 대처 방법이 달라지기 때문입니다.

우선 일시적이 피크라면 그 시점에 어떤 작업이 실행되었는지를 확인합니다. 특정 연산이 CPU를 많이 소모하는지, 배치 프로세스가 겹쳤는지, 혹은 특정 시간대에 트래픽이 몰렸는지를 확인합니다. 또한, 해당 현상이 일시적인 현상으로 파악된다면 우선 모니터링을 하고, 반복되는 패턴을 보인다면 배치를 분산시키거나, 리팩토링을 통해 cpu 사용량을 최적화하는 식으로 문제를 해결합니다.

CPU 사용량이 일정 수준에서 계속 유지된다면 어떤 프로세스가 CPU를 점유하고 있는지 확인합니다. 워커 수가 과도한지, 특정 서비스가 반복적으로 CPU를 잡고 있는지, 병렬 처리 설정이 과한지 등을 하나씩 점검합니다. 줄일 수 있는 부분이 있다면 먼저 튜닝으로 해결을 시도합니다. 그래도 평균 사용률이 계속 높게 유지된다면, 그때는 확장을 고려합니다.

### CPUs

서버의 CPU 코어 개수입니다. 단독으로 확인하기보다는 아래 Load Average를 해석할 때 참고용으로 사용하고 있습니다.

### Load Average

Load Average는 처음에는 익숙하지 않은 지표였습니다. CPU 사용량이 훨씬 직관적이었기 때문에 CPU 사용량 지표를 더 자주 확인했습니다. 하지만 두 지표 모두 중요하게 봐야 하는 지표입니다. 

CPU 사용량이 '지금 CPU가 얼마나 바쁜지'를 나타낸다면 Load Avarage는 'CPU를 사용하려고 하는 작업이 얼마나 쌓여있는지'를 보여주는 지표입니다. CPU Usage가 현재 사용 중인 비율이라면, Load Average는 작업 대기 줄의 길이에 가깝습니다.

그렇기 때문에 CPU 코어 개수와 함께 봐야 합니다. 제가 운영하는 서버는 CPU 코어가 총 8개입니다. Load가 8 이하라면 모든 작업이 요청과 동시에 CPU에 배정되어 처리된다는 뜻이고, Load가 8을 넘어가게 되면 일부 작업은 대기상태에 들어갔다는 뜻입니다.

운영하면서 느낀건 CPU 사용량 보다 Load가 훨씬 더 체감 성능과 연결된다는 점이었습니다. CPU 사용량이 80%를 넘더라도 Load가 코어 수 이하로 유지되면 서비스는 비교적 안정적으로 동작합니다. 반면 CPU 사용량은 높지 않은데 Load가 코어 수를 초과한 상태가 지속된다면 응답 지연이 발생하며 이는 사용자 경험 하락으로 직결됩니다.

그렇기 때문에 저는 요즘 Load Average 지표를 더 중요하게 확인합니다. Load가 코어수를 넘는다면 해당 시점에 몰리는 CPU 사용량을 분산시키려고 노력합니다.

현재 운영하고 있는 플랫폼에서는 다양한 오디오 파일 형식을 지원합니다. 다만 처리 파이프라인의 일관성을 위해 모든 파일을 mp3로 변환하여 함께 저장합니다. 이 과정은 유저에게 노출되지 않고 내부적으로 처리됩니다.

그런데 바로 이 mp3 파일을 검증해야 하는 상황이 발생했습니다. UI에 mp3 다운로드 버튼을 추가해서 다운로드 하는 방법도 있었지만, 빠르고 또 간단하게 해결하고 싶었습니다. 

그러다가 API 응답으로 전달된 mp3 Blob 데이터를 바로 다운받을 수 있다면 간단하게 검증할 수 있지 않을까? 하는 생각이 들었습니다. 여러가지 방법을 시도한 끝에 개발자 도구에서 자바스크립트를 사용하면 임시로 다운받을 수 있다는 것을 확인하였습니다. 저와 비슷한 상황을 겪고 계실 분들께 도움이 될까 싶어 과정 전체를 정리해봅니다.

## 2. 콘솔에서 Base64 데이터를 mp3 파일로 변환

이제 개발자 도구의 `Console` 탭으로 갑니다.
콘솔 창에서 복사한 Base64 문자열을 아래와 같이 변수로 선언합니다.

```javascript
const base64Data = "{복사한 Base64 데이터}"; 
```

<p><img src="/assets/images/251119/04.png" /></p>

아래 코드를 통해 변수에 할당된 Base64 데이터를 mp3 파일로 변환하여 다운로드 합니다.

```javascript
const link = document.createElement('a');
link.href = 'data:audio/mpeg;base64,' + base64Data;
link.download = 'download.mp3';
link.click();
```

<p><img src="/assets/images/251119/05.png" /></p>

그럼 아래 스크린샷과 같이 mp3 파일이 바로 다운로드 되는 것을 확인할 수 있습니다.

<p><img src="/assets/images/251119/06.png" /></p>

물론 이 방법은 빠르게 확인하기 위한 임시적인 우회 방법에 가깝습니다. 그럼에도 UI 변경이나 별도 스크립트 배포 없이, 개발자 도구만으로 문제를 빠르게 검증할 수 있어서 실제 운영 중 꽤 유용하게 활용했습니다.
